# 情报官

2026-09-17：基于 **OpenAI Agents SDK** 的[独立播客研究 Agent](docs/PODCAST_AGENT.md)已在 Railway 启用公开播客档案模式，支持来源查询、对话新增追踪、更新查询、全文问答及文字稿附件。组织飞书文档归档/检索尚未启用，与上述功能独立；新部署仍需显式配置模式与访问白名单。

情报官把飞书限定为交互界面：它接收私聊或群内 @，并把结果发回飞书。播客发现、完整文字稿核验、OpenAI 摘要、定时任务、队列与状态全部运行在一个常驻云容器中，因此电脑关机后仍能工作。

私聊与已授权群聊使用同一个 Agent、同一份正式播客全文库和日报归档。在群里任何成员都可以 @ 机器人提问；私聊访问仍由用户白名单控制。对话历史按会话和发言人隔离，不将私聊或其他同事的历史用作回答依据。`发一下今天的日报` 通过 `get_daily_digest` 读取当日已生成的正式日报，不等同于查询过去 24 小时 RSS 目录；未生成时明确说明。新节目分析保留 RSS 音频与字幕元数据，走与日报相同的全文获取链路。

服务通过飞书官方 WebSocket 长连接收消息，不需要公网回调、Vercel、Verification Token 或逐条触发 GitHub Actions。每个请求先进入 SQLite 持久队列；分析结果和每个收件人的每一段消息再固化到 outbox 后才发送。网络中断、容器重启或单个无效收件人都不会导致重新调用模型、消息混段或阻塞其他群。

群聊和私聊的最终回答也默认合成一条消息，不再按 3,500 字节拆开；保留内部段落和引用。富文本超限时先用单条纯文本，只有连纯文本也超过平台容量才按实际 UTF-8 请求大小拆分，绝不截断正文。单次请求中的多段结果先合并，再持久化排版；重试仍使用相同 UUID 和内容。升级前已准备的旧消息保持原样完成。明确索取的附件、耗时任务的处理中提示和故障通知仍是独立消息。

代码按 `Feishu adapter → command plugins → podcast service → transcript providers → persistent store/outbox` 分层。新增搜索、公司研究等能力时，实现一个独立 plugin 并在 `CommandRouter` 注册即可；只有新能力确实要访问飞书文档、日历等资源时，才需要增量申请相应飞书权限。

## 云端文件记忆

公开播客档案模式同时保留 SQLite 核验记录与文件库。文件库默认位于数据库旁的 `podcast-memory/`；Railway 上为 `/data/podcast-memory`，可用 `NEWS_OFFICER_MEMORY_PATH` 配置，且必须落在持久卷内。启动时补齐历史全文，每分钟归档新内容；Agent 检索前也同步一次，然后从校验后的文件读取原文。关键词检索覆盖全部已归档节目，不再只限最近 200 期，模型只接收本轮相关片段。

每期包含 `transcript.txt`（核验原文逐字保留）、`metadata.json`（标题、来源、日期、完整性和哈希），以及已有摘要时的 `summary.md`。文件按节目、单期与内容版本组织，根目录 `index.json` 指向当前版本。摘要与原文分开，更新保留旧版。写入采用临时文件与原子替换；已有不可变文件若被改动，不覆盖，也不作为问答证据。

这是原文资料记忆，不是模型自动训练。文件库不包含私聊或群聊历史，不自动收录任意手工放入的文件，也不依赖组织云文档权限。它默认不发送全文附件。文件目录已加入 Git/Docker 忽略规则；协作仓库只放代码和说明，不放全文、数据库或密钥。备份时请同时保留 SQLite 与文件目录；同一持久卷并不等于异地灾备。

## 文字稿规则

日报默认只通过节目官方 RSS 发现新集和核验发布时间，不扫描 YouTube 频道、不抓取 YouTube 元数据或字幕。全文按“已有核验存档 → RSS/官网官方文字稿 → Podwise”顺序获取。只有来源明确、文本密度达标且覆盖节目主体时才会调用模型；否则固定回复“未取得完整文字稿，本次不摘要”。当前已接入 Acquired、Dwarkesh、Lenny's Podcast、The Generalist、David Senra、Sequoia、Invest Like the Best/Colossus 等官方来源。用户主动发来的 YouTube 链接仍支持分析，且 Podwise 优先于字幕兜底。

新生成的晨报采用连贯短段落：每期先给“嘉宾或节目｜中文核心主题”，交代节目、链接和时长，再用两段为主（最多三段）的正文讲清核心判断、推理及重要分歧，最后给出一句推荐理由和阅读建议。正文通常 300–500 字，不列编号要点，不反复使用“嘉宾观点”等标签；预测和公司自报数据用“预计”“公司称”等自然措辞保留必要归属。全文核验规则不变，自动精读文档仅面向五星节目。历史摘要兼容读取，已经冻结的消息和文字稿校验哈希不作改写。

`NEWS_OFFICER_DAILY_RSS_ONLY=true` 为运行时默认值，全部 14 个内置关注源均已有 RSS。RSS 失败会明确报告，不静默退回 YouTube；新增来源没有 RSS 时需补齐 RSS。RSS 每源至少扫描最近 30 条（候选不限时扫描完整 feed），再按追踪窗口筛选。已有更新但缺少全文、日期未核验、摘要格式失败时，会单独列出数量和部分节目。历史合并的 YouTube ID 通过相同节目名、标题和发布时间去重，切换来源不会重发已处理的同一期。此开关不触发当天日报重跑，也不新增自动补跑时段。

日报对每期已取得完整文字稿的节目生成摘要，按星级从高到低展示，低分不剔除。评分只看相关度和信息密度：model frontier、AI research，以及 Fireworks 这类 AI 公司创始人的一手深度访谈优先；其中，OpenAI、Anthropic 等模型实验室的实质讨论，以及热门 AI 独角兽创始人（如用户指定的 Fireworks）的主要受访节目，作为必收录内容，至少归为“值得看全文”。广告、顺带提名和标题党不算；信息密度仍如实判断，不自动升为编译档。内部公司名单不单独加分。五星“值得编译”是少数双项满分的内容；四星“值得看全文”；三星“看摘要”。允许当天没有五星。用户只看到“值得编译 / 值得看全文 / 看摘要 / 无关”和推荐理由，不显示星星或分项分数；缺全文属于待处理，不归为无关。详见 [评分规则](docs/editorial-policy.md)。历史已发送消息不重写。

日报默认合并发送：各期推荐理由、正文、阅读建议及待处理状态放在同一条富文本消息内，不再每期单独推送。按实际序列化请求大小检查飞书限制；富文本过长时优先改为一条纯文本，极端超长才无损分段，不删减节目。每批内容及其节目映射先持久化，再发送；重启后重放同一消息，不重新生成。引用整份日报时，Agent 可看到其中的节目列表和资料编号。旧版已准备的消息保持原样完成，全文附件模式沿用旧格式；可用 `NEWS_OFFICER_DAILY_COMBINED_MESSAGE=false` 临时回退。

### Podwise 扩展发现：不局限于关注列表

开启 `NEWS_OFFICER_PODWISE_DISCOVERY=true` 后，晨报同时扫描 Podwise 热门榜、AI 主题搜索和相关频道的新集目录，在同一个 24 小时时间窗内寻找列表外的节目。先与 RSS 和已推送历史去重，再取得完整文字稿并按现有规则推荐；符合编译档的也会生成飞书文档。正文标注“Podwise 扩展发现”，不会自动长期订阅该频道。探索中不值得推荐的内容只汇报数量，原有关注源仍保持完整摘要覆盖。

这不是 Podwise 全站新集的穷尽扫描：接口没有完整的按发布时间排序的新集入口，搜索与目录都有读取上限；失败和截断会明确报告。列表外节目只读取现有全文，不自动提交付费转写。部署配置、边界和无发送验收脚本见 [扩展发现说明](docs/podwise-discovery.md)。

### Podwise 全文获取与授权

配置云端 Secret `PODWISE_API_TOKEN` 后，在存档和官网适配器之后尝试 Podwise；日报不再尝试 YouTube 字幕。需要 Podwise Pro/Enterprise，在 Settings → Developer 生成 token；不要把 token 提交到 Git、粘贴到聊天或日志中。未配置时不访问 Podwise，不能宣称已接通。Podwise 时长缺失时，只有已核验为同一期且 RSS 提供独立时长，才用 RSS 时长进行全文覆盖校验，不以最后一句时间戳自行认定完整。

跨版本全文按节目核心标题、已知节目名称别名和相近发布日期核验，再用独立 RSS 时长检查全程覆盖及 Podwise 完成状态；不做模糊标题猜配，也不直接抓取 YouTube。设置 `PODWISE_AUTO_PROCESS=true` 后，只有正式日报中可唯一匹配的 RSS 节目才会自动提交 Podwise 转写，使用现有套餐额度，不自动购买、不导入私人音频。提交前将资产编号写入持久化去重账本；请求超时不盲目重发，失败任务不自动重复扣费重启。

缺全文节目保留原始 RSS 身份进入持久待办，每 30 分钟检查并在完成后补发（连续一天仍不可用则降到每 6 小时）。补发沿用日报当前订阅收件人，不受原始 24 小时发现窗口限制，不重复发送已送达节目。未找到记录、等待转写、额度不足和校验失败分别说明；程序不能保证第三方始终能提供全文。普通聊天不会自动消耗转写额度。

顺序为已有核验归档 → 官网/RSS 全文 → 公共字幕 → Podwise。仅使用官方 Open API 的读取接口，不调用处理/导入接口，不发起付费转写。按原始链接匹配，或严格匹配标题、节目名、日期和时长；RSS 音频与 YouTube 均有转写时优先精确匹配 RSS enclosure，同一音频多个已处理版本仍拒绝歧义。获取后再次核对身份，检查首尾与中间覆盖、文本密度，搜索片段和 AI 摘要不充当全文。时间轴小幅超出元数据时，只有差异不超过 5%、独立 status 接口确认 done/100、且较长时间轴本身通过全文覆盖校验才接受；缺中段仍拒绝。仅有起点时间戳时采用更保守门槛。当前文本密度规则面向英文播客。

授权前只能验证模拟接口，真实覆盖率需配置 token 后确认。可运行 `scripts/smoke_podwise.py` 检查四个来源各最新一期、过去 72 小时内的节目；加 `--summarize` 会使用现有模型测试其中最短一期的全文摘要和附件，仅写临时数据库，不发送飞书消息。这不是全来源覆盖率报告。

真实接口兼容性：Podwise 的原始链接可能是音频地址，需与 RSS enclosure 匹配；未处理的重复索引不阻挡唯一已转写版本，但多个已转写匹配仍拒绝猜选。数字时间戳的秒/毫秒单位以独立的可读时间戳逐段交叉核验，不按数值大小猜测。容许源音频末尾小幅超出 RSS 标注时长，但首尾与中段完整性门槛不变。

401 表示 token 问题，402 表示套餐/用量受限，429 表示限流；失败不降级为猜测摘要。参考 [授权文档](https://docs.podwise.ai/open-api-v1/basics/authorization)、[搜索 API](https://docs.podwise.ai/open-api-v1/discovery/search-episodes)、[文字稿 API](https://docs.podwise.ai/open-api-v1/get-episode-transcripts)。

## 精编文字稿与交互问答

成功生成摘要后，情报官仍把核验过的全文保存在云端，用于后续问答；**日报和链接分析默认不发送文字稿附件**。只推送推荐理由、十条以内短要点、推荐星级及收听链接。用户明确索取文字稿时才生成 Markdown 阅读版；清理只作用于阅读版，不覆盖原始全文或其校验值。

`NEWS_OFFICER_MAX_SUMMARIES=0` 与 `NEWS_OFFICER_MAX_CANDIDATES=0` 表示处理追踪时间窗内发现的全部未推送候选，不再精选三期后停止；RSS 扫描不再只取前 30 条。已推送去重、缺全文重试冷却、日期和全文核验继续生效。所有取得完整正文的节目均生成摘要及推荐；缺全文仍不能凭标题编写推荐。可用正整数恢复数量限制。`NEWS_OFFICER_DAILY_TRANSCRIPT_ATTACHMENTS=false` 为默认值；显式设为 `true` 可恢复日报附件。多期处理顺序执行，数量增加会延长运行时间并增加模型用量。

自然语言是默认交互方式。情报官会先判断用户是在问候、找节目、索取文字稿、追问节目内容，还是管理日报订阅；模型只负责意图和节目定位，不能直接编造播客答案。节目选定后，事实回答仍由完整原始文字稿和逐字引用校验约束。正文明确提到的新节目优先于被回复消息和旧会话上下文，避免在错误节目上作答。

可以直接这样说：

- `Sam Altman 在 Dwarkesh 那期怎么看 Agent？`
- `那他为什么这么判断？`
- `把这期完整文字稿发我。`
- `最近有什么值得听的？`
- `帮我订阅每天的播客日报。`

公司名/嘉宾名也可以作为找节目的起点，例如“最近听说 Town 的 founder CEO 的播客不错，重点总结一下”。Agent 先查全文档案，再使用 `search_episodes` 查追踪源的 RSS 标题与简介（默认 90 天，每源最多 100 期，匹配后返回最多 12 个候选）；这不改变日报的 24 小时窗口。模型根据公司、嘉宾身份和发布时间选择明确候选，自主获取全文、阅读并回答。只有真实候选仍有歧义才追问；不能把库里没有当作网上没有，也不能用简介冒充全文。该工具不是全网搜索，覆盖范围和来源失败会明确返回。可运行 `scripts/smoke_episode_discovery.py` 用真实模型、RSS 和全文服务验收原始 Town 问法；只写临时状态，不发送飞书消息、不启动付费转写。

情报官会保留最近 4 轮有界对话历史，用于理解“他”“这期”“刚才第二点”等追问；这段历史只用于消解指代，不能作为节目事实证据。匹配到多期时可以自然地说“第二个”“最新那期”或回复标题关键词。

以下旧命令继续兼容；在群聊中先 @ 情报官：

- `最近播客`：列出资料库中最近可提问的节目及编号。
- `文字稿 <编号/节目/嘉宾>`：获取匹配节目的精编可读版 Markdown 文字稿；原始核验全文仍用于问答与核验。
- `问 <编号> <问题>`：针对指定节目提问，例如 `问 a1b2c3d4 嘉宾如何判断 AI 应用的护城河？`。
- 也可以自然地问 `整理某某的观点`、`某某为什么看好这个市场？`。如果当前对话已经选中过一期节目，情报官会在没有新节目锚点时沿用该上下文。
- 当节目或嘉宾名称匹配到多期内容时，情报官会返回候选列表；回复 `选 1`、`选 2` 等即可继续。

所有回答都只依据资料库中的原始、完整、可核验文字稿，并附上内部原文定位编号。文字稿没有明确说到的内容会直接说明“文字稿中未找到依据”，不会用节目简介、常识或模型推测补齐。若原始文字稿没有可靠的说话人标签，回答也会提示归因限制。

## 飞书最小配置

应用名建议设为“情报官”，只需要四个应用身份权限：

- `im:message.p2p_msg:readonly`
- `im:message.group_at_msg:readonly`
- `im:message:send_as_bot`
- `im:resource`

事件只订阅 `im.message.receive_v1`，接收方式选择长连接。`im:resource` 仅用于上传和发送精编文字稿文件。私聊可直接发链接或发送“订阅”“退订”“帮助”；群聊中 @ 情报官后使用相同功能。“订阅”会把当前私聊用户或当前群持久加入日报收件人。下面的官方一键注册流程会生成一个只含上述权限的确认页。确认一次后，脚本会配置 `lark-cli`，并把 App Secret 安全存入 macOS 系统钥匙串，全程不显示明文：

```bash
uv run --with lark-oapi==1.7.3 python scripts/register_feishu_app.py
```

## Railway 部署

仓库根目录的 `Dockerfile` 会被 Railway 自动识别。服务必须保持一个 replica、关闭 Serverless 休眠，并把持久卷真实挂载到 `/data`。付费计划可将 restart policy 设为 `Always`；Free/Trial 计划使用其允许的 `On Failure`（最多 10 次）。程序在 Railway 上会主动校验卷；配置错误时宁可启动失败，也不会把去重和队列状态悄悄写入临时磁盘。

配置 `.env.example` 中的变量后启动。核心变量是 `FEISHU_APP_ID`、`FEISHU_APP_SECRET` 和 `OPENAI_API_KEY`。`FEISHU_USER_OPEN_IDS` 与 `FEISHU_GROUP_CHAT_IDS` 是可选的初始订阅种子；此后用户和群可以直接在飞书中订阅或退订，状态保存在 SQLite。退订会跨重启保留，即使旧 ID 仍留在环境变量中也不会被重新加入。密钥应通过 Railway Variables 或 CLI stdin 写入，不进入仓库与命令行参数。

推荐使用初始化脚本。它默认只预览计划；加 `--apply` 后才会检查已登录的 Railway CLI，创建项目（或关联已有项目）、准备 `news-officer` service、挂载 `/data`，并用 `--skip-deploys` 写入变量。它不会部署服务，也不会创建或升级付费套餐：

```bash
# 首次创建：先预览，再执行
uv run scripts/bootstrap_railway.py --create-project
uv run scripts/bootstrap_railway.py --create-project --apply

# 或关联一个已有 Railway 项目
uv run scripts/bootstrap_railway.py --project-id <project-id> --apply
```

脚本从 lark-cli 当前 profile 读取 App ID，并解密其系统钥匙串引用。两个 Secret 只通过子进程 stdin 写入 Railway，既不出现在命令参数中，也不会打印或写入仓库。`OPENAI_API_KEY` 优先从同名环境变量读取；没有时使用隐藏输入。管道场景可加 `--openai-key-stdin`。初始化成功后，再单独执行脚本提示的 `railway up` 命令部署，便于把“准备配置”和“实际上线”分成两个清晰动作。

默认每天北京时间 08:30 扫描过去 72 小时内的新节目，最多摘要 3 期。所有已检查节目、消息幂等键和任务状态都保存在 `/data/news-officer.sqlite3`。

## 一起贡献

### 重点播客：一期一篇飞书精读

设置 `NEWS_OFFICER_DAILY_DOCUMENT=true` 后，早间文字日报的内容、筛选范围和发送方式保持不变。先确认日报发送完成，再从同一份日报清单选择 **五星“值得编译”的每一期**，分别编译成独立飞书文档，不生成每日合集。默认门槛为 `NEWS_OFFICER_DAILY_DOCUMENT_MIN_STARS=5`；没有符合条件的节目就不另发空通知。编译完成、写入回读和群阅读授权都通过后，把本批文档链接合在一条补充消息里，每期链接只出现一次。编译不阻塞问答或文字日报。`NEWS_OFFICER_DAILY_DOCUMENT_START_DATE=YYYY-MM-DD` 限定启用日期，最多回看最近七天；`NEWS_OFFICER_DAILY_DOCUMENT_FOLDER` 可配置机器人有写入权限的文件夹，留空则创建在机器人根目录。

每日任务和交互请求共同加载 `src/news_officer/prompts/podcast_shownotes.md`。这是用户提供的 `podcast-notes-feishu` 的章节笔记适配版，不声称完整执行版：保留原始英文标题、浅蓝信息框、6–9 条带时间戳核心论点、章节英文短引、中文要点和原生对比表，不附完整实录或整期翻译，不加编者评论。有节目说明章节时按其顺序，章节太多才合并为 8–12 章；没有官方章节时按话题分章，不强行凑数。引文必须逐字匹配，合计最多 25 个单词；时间戳定位到原稿发言，ASR 订正须有依据。输入必须是已核验全文，不用简介补写。自动任务继续使用现有官方全文/RSS/Podwise 取稿链路，不依赖用户电脑上的浏览器。

同事在已授权群中 @机器人要求重点总结、详细版或做文档时，Agent 先结合引用消息与会话上下文定位节目、取得全文，再调用 `create_episode_document`。这条入口不受星级限制，不要求该群订阅日报，也不限于管理员；私聊仍沿用已授权用户列表。任务完成后回复原消息里的一个文档链接，而不是再次发一整篇长聊天。一般观点追问仍直接回答。排队、失败与完成状态分开，不在成品通过读回和权限检查前承诺成功。

同一期跨日报去重，原稿修订在同一篇节目文档追加更新。补齐全文且达到门槛的其他节目另建文档。以前已经发过的每日合集保留，不再自动更新或生成新合集。结构化精读缓存在 SQLite，Markdown 留存在数据库同目录的 `daily-shownotes/`（Railway 为 `/data/daily-shownotes/`）；原始文字稿长期档案不删除。写入中断可从回读确认的段落继续；检测到人工修改时停止覆盖。创建回执丢失时先按标题核对，不盲目重复建文档。

该功能额外需要机器人创建/读取/编辑云文档、列出目标文件夹和管理文档协作者的权限。订阅群只获得该日文档的阅读权限，不开启互联网公开访问，也不读取公司其他文件。权限缺失时不会发送一个尚未完成或未授权的文档链接。

项目通过 GitHub Pull Request 协作。请从最新的 `main` 创建短生命周期分支，完成修改和测试后提交 PR；不要直接把功能分支长期堆在 `main` 上。CI 会自动执行 Ruff、单元测试与 Python 编译检查。

新增播客源时，PR 必须说明节目官方来源、完整文字稿的取得方式，以及文字稿不完整时的失败行为。任何 App Secret、API Key、用户或群聊 ID 都不得提交到仓库；本地配置放在未跟踪的 `.env`，云端密钥放在 Railway Variables。
